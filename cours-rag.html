Pourquoi RAG ?

Problèmes des LLMs

  • Hallucinations : inventent des réponses
  • Données privées : n'ont pas accès à vos docs
  • Fraîcheur : entraînés à une date fixe

Solution : RAG

Donner au LLM les bons documents au moment de la question, pour qu'il réponde à partir de faits réels.

Section 1

Les LLMs et leurs limites

Comment fonctionne un LLM ?

Le principe : prédire le prochain mot (token) le plus probable

"Le chat est sur le ___"

TokenProbabilité
toit34%
canapé22%
lit18%
sol12%

Un LLM ne "comprend" pas — il calcule des probabilités sur des séquences de tokens

La tokenisation

"Bonjour, comment allez-vous ?"

↓

Bon jour , comment allez - vous ?

Un mot ≠ un token. Les mots longs ou rares sont découpés en sous-mots.

La fenêtre de contexte

On ne peut pas copier-coller 10 000 documents dans le prompt !

Les hallucinations

Question : "Quelle est la politique de remboursement de notre entreprise ?"

LLM sans RAG : "Votre entreprise offre un remboursement sous 30 jours avec un formulaire RH-42..."

Totalement inventé ! Le LLM ne connaît pas vos documents internes.

LLM avec RAG : "D'après le document 'politique-rh.pdf', les remboursements se font sous 14 jours via le portail interne."

Basé sur un vrai document, avec une source citée.

Données privées et fraîcheur

Données privées

  • Docs internes d'entreprise
  • Base de connaissances interne
  • Contrats, rapports...

Le LLM n'a jamais vu ces documents !

Fraîcheur des données

  • LLM entraîné à une date fixe
  • Ne connaît pas les news récentes
  • Docs mis à jour après l'entraînement

Impossible de répondre sur l'actualité

Pipeline d'ingestion

Vue d'ensemble du pipeline

Le pipeline dans le code


# src/ingestion/pipeline.py — fonction ingest_document()

def ingest_document(content, filename, content_type, collection=None):
    document_id = uuid.uuid4().hex

    try:
        # 1. Parse : extraire le texte brut du fichier
        text = parse_document(content, content_type, filename)

        # 2. Chunk : découper en morceaux
        chunks = chunk_text(text, document_id, metadata={...})

        # 3. Embed & Store : vectoriser et sauvegarder
        store = get_vector_store(collection=collection)
        store.add_chunks(chunks)  # embed_texts() appelé à l'intérieur

    except Exception as exc:
        metadata.status = DocumentStatus.FAILED

Parsing multi-format


# src/ingestion/parser.py
SUPPORTED_TYPES: dict[str, str] = {
    "text/plain": "text",
    "text/markdown": "text",
    "text/csv": "text",
    "application/pdf": "pdf",
    "application/vnd.openxmlformats-officedocument.wordprocessingml.document": "docx",
}

def parse_document(content: bytes, content_type: str, filename: str) -> str:
    """Extract plain text from a document based on its content type."""
    parser_key = SUPPORTED_TYPES.get(content_type)

    if parser_key == "text":
        return _parse_text(content)
    elif parser_key == "pdf":
        return _parse_pdf(content)
    elif parser_key == "docx":
        return _parse_docx(content)

def _parse_pdf(content: bytes) -> str:
    from pypdf import PdfReader
    reader = PdfReader(io.BytesIO(content))
    pages = []
    for page in reader.pages:
        text = page.extract_text()
        if text:
            pages.append(text)
    return "\n\n".join(pages)

Pourquoi découper en chunks ?

Analogie

Imaginez chercher une info dans un livre de 500 pages...

  • On ne lit pas tout le livre !
  • On regarde l'index
  • On va à la bonne page

Pour le RAG

  • Un document = trop gros pour le prompt
  • Un chunk = un "paragraphe" pertinent
  • On cherche les chunks pertinents, pas le document entier

Le découpage récursif


# src/ingestion/chunker.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

def chunk_text(text, document_id, metadata=None):
    settings = get_settings().chunking

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=settings.chunk_size,       # 512 caractères
        chunk_overlap=settings.chunk_overlap,  # 50 caractères
        separators=settings.separators,        # ["\n\n", "\n", ". ", " "]
        length_function=len,
    )

    raw_chunks = splitter.split_text(text)
    # Résultat : liste de strings, chacune ≤ 512 caractères
    # avec 50 caractères de chevauchement entre chunks consécutifs

Récursif = essaie d'abord de couper aux paragraphes (\n\n), puis aux lignes (\n), puis aux phrases (. ), puis aux espaces ( )

Paramètres du chunking


# config/settings.yaml
chunking:
  strategy: recursive
  chunk_size: 512
  chunk_overlap: 50
  separators: ["\n\n", "\n", ". ", " "]

Trade-offs : taille des chunks

Petits chunks (128-256)

  • Précis : réponse ciblée
  • Moins de bruit
  • Perd le contexte
  • Plus de chunks à indexer

Grands chunks (1024+)

  • Plus de contexte
  • Moins de chunks
  • Plus de bruit
  • Moins précis

Notre choix : 512 caractères avec overlap de 50 — bon compromis pour des documents techniques

Chaque chunk est identifié


# src/ingestion/chunker.py — création des objets Chunk
for idx, raw in enumerate(raw_chunks):

Section 3

Embeddings

Transformer du texte en vecteurs

C'est quoi un embedding ?

Un embedding = une représentation numérique d'un texte

"Le chat dort sur le canapé"

↓

[0.023, -0.156, 0.892, 0.034, ..., -0.445, 0.231]

384 nombres à virgule flottante (dimensions)

L'idée clé : des textes au sens similaire produisent des vecteurs proches

Visualisation : mots proches = vecteurs proches

Le modèle all-MiniLM-L6-v2

PropriétéValeur
Dimensions384
Taille du modèle~80 MB
Vitesse~14 000 phrases/sec (GPU)
Longueur max256 tokens
Entraîné sur1 milliard de paires de phrases
LangueMultilingue (dont le français)

Choisi pour notre projet car : léger, rapide, gratuit, tourne en local sans GPU

Sentence-Transformers


# src/retrieval/embeddings.py
from functools import lru_cache
from sentence_transformers import SentenceTransformer
from src.core.config import get_settings

@lru_cache(maxsize=1)  # Charger le modèle une seule fois !
def _load_model() -> SentenceTransformer:
    settings = get_settings().embeddings
    model = SentenceTransformer(settings.model)  # "all-MiniLM-L6-v2"
    return model

def embed_texts(texts: list[str]) -> list[list[float]]:
    """Générer les embeddings pour une liste de textes."""
    model = _load_model()
    embeddings = model.encode(texts, normalize_embeddings=True)
    return embeddings.tolist()

def embed_query(query: str) -> list[float]:
    """Générer l'embedding pour une question."""
    model = _load_model()
    embedding = model.encode(query, normalize_embeddings=True)
    return embedding.tolist()

Pourquoi normaliser ?

normalize_embeddings=True rend tous les vecteurs de norme 1

Avantage : la distance cosinus devient un simple produit scalaire

Calcul beaucoup plus rapide pour la recherche !

Similarité cosinus

Cosinus vs Euclidienne

Distance Euclidienne

Mesure la distance absolue entre deux points

Sensible à la longueur des vecteurs

Un texte long et un texte court sur le même sujet peuvent sembler "loin"

Similarité Cosinus

Mesure l'angle entre deux vecteurs

Insensible à la longueur

Deux textes sur le même sujet sont "proches" quelle que soit leur taille

C'est pourquoi ChromaDB utilise "hnsw:space": "cosine"

Quiz : quels textes sont proches ?

Texte A : "Le Python est un excellent langage de programmation"

Texte B : "Le python royal est un serpent non venimeux"

Texte C : "JavaScript et TypeScript sont des langages web"

PaireSimilarité
A ↔ B~0.35 (mots communs mais sens différent)
A ↔ C~0.72 (même domaine : programmation)
B ↔ C~0.12 (rien à voir)

L'embedding capture le sens, pas juste les mots-clés !

# src/retrieval/vector_store.py
import chromadb
from pathlib import Path
from src.core.config import get_settings

class VectorStore:
    def __init__(self, collection_name=None):
        settings = get_settings().vector_store
        persist_dir = settings.persist_directory
        Path(persist_dir).mkdir(parents=True, exist_ok=True)

        # Client persistant : les données survivent au redémarrage
        self._client = chromadb.PersistentClient(path=persist_dir)

        # Collection = une "table" dans ChromaDB
        self._collection = self._client.get_or_create_collection(
            name=name,
            metadata={"hnsw:space": "cosine"},  # Similarité cosinus !
        )

Ajouter des chunks


# src/retrieval/vector_store.py — méthode add_chunks()
def add_chunks(self, chunks: list[Chunk]) -> None:
    texts = [c.text for c in chunks]
    ids = [c.chunk_id for c in chunks]
    metadatas = [{**c.metadata, "document_id": c.document_id} for c in chunks]

    # Générer les embeddings pour tous les chunks
    embeddings = embed_texts(texts)

    # Stocker dans ChromaDB
    self._collection.add(
        ids=ids,              # identifiants uniques
        documents=texts,      # texte original (pour le retourner)
        embeddings=embeddings,# vecteurs 384D
        metadatas=metadatas,  # métadonnées (filename, etc.)
    )

Rechercher par similarité


# src/retrieval/vector_store.py — méthode search()
def search(self, query, top_k=5, score_threshold=0.3):
    query_embedding = embed_query(query)

    results = self._collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k,
        include=["documents", "metadatas", "distances"],
    )

    sources = []
    for idx, chunk_id in enumerate(results["ids"][0]):
        # ChromaDB retourne la distance cosinus → convertir en score
        distance = results["distances"][0][idx]
        score = 1.0 - distance  # distance 0 → score 1 (identique)

        if score < score_threshold:  # Filtrer les résultats trop faibles
            continue

        sources.append(SourceDocument(
            chunk_id=chunk_id,
            text=results["documents"][0][idx],
            score=round(score, 4),
        ))
    return sources

Distance → Score de similarité

score = 1.0 - distance_cosinus

DistanceScoreSignification
0.01.0Textes identiques
0.30.7Très similaires
0.70.3Seuil par défaut
1.00.0Sans rapport

Notre score_threshold = 0.3 filtre les chunks dont le score est trop bas

def query(request: QueryRequest) -> QueryResponse:

    sources = store.search(

store.search() appelle embed_query() en interne pour vectoriser la question, puis fait une recherche HNSW dans ChromaDB

Étape 3 : Construction du contexte


# src/retrieval/rag_engine.py
def _build_context_block(sources: list[SourceDocument]) -> str:
    parts = []
    for i, src in enumerate(sources, 1):
        header = f"[Source {i} | score={src.score}]"
        meta_str = ", ".join(
            f"{k}={v}" for k, v in src.metadata.items()
            if k != "chunk_index"
        )
        if meta_str:
            header += f" ({meta_str})"
        parts.append(f"{header}\n{src.text}")
    return "\n\n---\n\n".join(parts)

Résultat : un bloc de texte structuré avec chaque source numérotée et son score

Le System Prompt


# src/retrieval/rag_engine.py
SYSTEM_PROMPT = """\

Answer questions using ONLY the provided context documents.

Rules:
1. Base your answer strictly on the context provided below.
2. If the context does not contain enough information

Clé du RAG : on ordonne au LLM de répondre uniquement à partir du contexte fourni. Cela réduit drastiquement les hallucinations.

@router.post("/documents/upload", status_code=201)
async def upload_document(
    file: UploadFile = File(...),     # Fichier multipart
    user: dict | None = Depends(get_current_user),
):
    content_type = file.content_type or "application/octet-stream"
    content = await file.read()       # Lire le contenu binaire
    filename = file.filename or "untitled"

    # Appeler le pipeline complet : parse → chunk → embed → store
    result = ingest_document(content, filename, content_type)

    if result.metadata.status == "failed":
        raise HTTPException(
            status_code=422,
            detail=f"Ingestion failed: {result.metadata.error}",
        )
    return result

Fine-tuning des embeddings

Entraîner le modèle d'embedding sur vos propres données pour améliorer la pertinence

Comment ?

  • Collecter des paires (question, chunk pertinent)
  • Fine-tuner le modèle avec ces paires
  • Le modèle apprend votre vocabulaire métier

Exemple : un modèle fine-tuné sur des docs juridiques comprendra mieux "clause résolutoire" qu'un modèle générique
