Glossaire : les mots-clés du cours

Tous ces termes seront expliqués en détail au fil du cours. Cette page sert de référence rapide.

TermeDéfinition simple
LLMLarge Language Model — un programme d'IA capable de comprendre et générer du texte (ex : ChatGPT, Claude)
RAGRetrieval-Augmented Generation — technique qui consiste à chercher des infos dans vos documents AVANT de demander à l'IA de répondre
TokenUn morceau de mot. Les LLMs ne lisent pas des mots entiers : ils découpent le texte en petits fragments appelés tokens

VecteurSynonyme d'embedding — une liste ordonnée de nombres (ex : [0.2, -0.5, 0.8])

PipelineUne chaîne d'étapes automatisées. Chaque étape prend le résultat de la précédente (comme une chaîne de montage)
APIApplication Programming Interface — un "guichet" qui permet à des programmes de communiquer entre eux via Internet
ModèleUn programme d'IA entraîné sur des données. Il en existe pour générer du texte (LLM) ou pour créer des embeddings

Pourquoi RAG ?

Problèmes des IAs de langage

  • Hallucinations : elles inventent des réponses quand elles ne savent pas
  • Données privées : elles n'ont jamais vu les documents de votre entreprise
  • Fraîcheur : leur connaissance s'arrête à leur date d'entraînement

Solution : RAG

Donner au LLM les bons documents au moment de la question, pour qu'il réponde à partir de faits réels.

Section 1

Les LLMs et leurs limites

Comment fonctionne un LLM ?

LLM = Large Language Model (grand modèle de langage). C'est un programme d'IA entraîné sur des milliards de textes (livres, sites web, articles...) pour apprendre à manipuler le langage. Exemples : ChatGPT, Claude, Gemini.

Le principe : prédire le prochain mot (token) le plus probable

"Le chat est sur le ___"

TokenProbabilité
toit34%
canapé22%
lit18%
sol12%

Un LLM ne "comprend" pas vraiment — il calcule des probabilités sur des séquences de mots. Mais comment lit-il ces mots exactement ? C'est ce qu'on va voir avec la tokenisation.

La tokenisation

"Bonjour, comment allez-vous ?"

↓

Bon jour , comment allez - vous ?

Un mot ≠ un token. Les mots longs ou rares sont découpés en sous-mots.

La fenêtre de contexte

Un LLM ne peut lire qu'une quantité limitée de texte à la fois. C'est sa fenêtre de contexte : tout ce qu'il "voit" pour formuler sa réponse.

On ne peut pas copier-coller 10 000 documents dans le prompt ! C'est pour ça qu'on a besoin du RAG.

Les hallucinations

Question : "Quelle est la politique de remboursement de notre entreprise ?"

LLM sans RAG : "Votre entreprise offre un remboursement sous 30 jours avec un formulaire RH-42..."

Totalement inventé ! Le LLM ne connaît pas vos documents internes.

LLM avec RAG : "D'après le document 'politique-rh.pdf', les remboursements se font sous 14 jours via le portail interne."

Basé sur un vrai document, avec une source citée.

Données privées et fraîcheur

Données privées

  • Docs internes d'entreprise
  • Base de connaissances interne
  • Contrats, rapports...

Le LLM n'a jamais vu ces documents !

Fraîcheur des données

  • LLM entraîné à une date fixe
  • Ne connaît pas les news récentes
  • Docs mis à jour après l'entraînement

Impossible de répondre sur l'actualité

L'idée du RAG

Section 2

Pipeline d'ingestion

Parse → Chunk → Embed → Store

Vue d'ensemble du pipeline

Avant de pouvoir chercher dans vos documents, il faut les préparer. C'est comme organiser une bibliothèque : on ne jette pas les livres en vrac — on les classe, on les indexe. Voici les 4 étapes de cette préparation :

Le pipeline dans le code


# src/ingestion/pipeline.py — fonction ingest_document()

def ingest_document(content, filename, content_type, collection=None):
    document_id = uuid.uuid4().hex

    try:
        # 1. Parse : extraire le texte brut du fichier
        text = parse_document(content, content_type, filename)

        # 2. Chunk : découper en morceaux
        chunks = chunk_text(text, document_id, metadata={...})

        # 3. Embed & Store : vectoriser et sauvegarder
        store = get_vector_store(collection=collection)
        store.add_chunks(chunks)  # embed_texts() appelé à l'intérieur

    except Exception as exc:
        metadata.status = DocumentStatus.FAILED

Parsing multi-format


# src/ingestion/parser.py
SUPPORTED_TYPES: dict[str, str] = {
    "text/plain": "text",
    "text/markdown": "text",
    "text/csv": "text",
    "application/pdf": "pdf",
    "application/vnd.openxmlformats-officedocument.wordprocessingml.document": "docx",
}

def parse_document(content: bytes, content_type: str, filename: str) -> str:
    """Extract plain text from a document based on its content type."""
    parser_key = SUPPORTED_TYPES.get(content_type)

    if parser_key == "text":
        return _parse_text(content)
    elif parser_key == "pdf":
        return _parse_pdf(content)
    elif parser_key == "docx":
        return _parse_docx(content)

def _parse_pdf(content: bytes) -> str:
    from pypdf import PdfReader
    reader = PdfReader(io.BytesIO(content))
    pages = []
    for page in reader.pages:
        text = page.extract_text()
        if text:
            pages.append(text)
    return "\n\n".join(pages)

Pourquoi découper en chunks ?

OK, on a extrait le texte brut de nos fichiers. Mais un PDF peut faire 50 pages ! On ne peut pas envoyer tout ça à l'IA. Il faut découper le texte en petits morceaux (chunks) pour pouvoir chercher précisément dedans.

Analogie

Imaginez chercher une info dans un livre de 500 pages...

  • On ne lit pas tout le livre !
  • On regarde l'index
  • On va à la bonne page

Pour le RAG

  • Un document = trop gros pour le prompt
  • Un chunk = un "paragraphe" pertinent
  • On cherche les chunks pertinents, pas le document entier

Le découpage récursif


# src/ingestion/chunker.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

def chunk_text(text, document_id, metadata=None):
    settings = get_settings().chunking

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=settings.chunk_size,       # 512 caractères
        chunk_overlap=settings.chunk_overlap,  # 50 caractères
        separators=settings.separators,        # ["\n\n", "\n", ". ", " "]
        length_function=len,
    )

    raw_chunks = splitter.split_text(text)
    # Résultat : liste de strings, chacune ≤ 512 caractères
    # avec 50 caractères de chevauchement entre chunks consécutifs

Pourquoi "récursif" ? L'algorithme essaie de couper intelligemment : d'abord entre les paragraphes (\n\n), si ça ne suffit pas, entre les lignes (\n), puis les phrases (. ), et en dernier recours, entre les mots ( ). Ainsi, on évite de couper au milieu d'une idée.

Paramètres du chunking


# config/settings.yaml
chunking:
  strategy: recursive
  chunk_size: 512
  chunk_overlap: 50
  separators: ["\n\n", "\n", ". ", " "]

Trade-offs : taille des chunks

Petits chunks (128-256)

  • Précis : réponse ciblée
  • Moins de bruit
  • Perd le contexte
  • Plus de chunks à indexer

Grands chunks (1024+)

  • Plus de contexte
  • Moins de chunks
  • Plus de bruit
  • Moins précis

Notre choix : 512 caractères avec overlap de 50 — bon compromis pour des documents techniques

Chaque chunk est identifié


# src/ingestion/chunker.py — création des objets Chunk
for idx, raw in enumerate(raw_chunks):
    chunk_id = f"{document_id}::{uuid.uuid4().hex[:12]}"
    chunks.append(
        Chunk(
            chunk_id=chunk_id,           # ID unique
            document_id=document_id,     # lien vers le document parent
            text=raw,                    # le texte du chunk
            metadata={
                "chunk_index": idx,      # position dans le document
                "total_chunks": len(raw_chunks),
                "filename": filename,
                "content_type": content_type,
            },
        )
    )

Les métadonnées permettent de retrouver l'origine de chaque chunk

Section 3

Embeddings

Transformer du texte en vecteurs

C'est quoi un embedding ?

Un embedding = une représentation numérique d'un texte

"Le chat dort sur le canapé"

↓

[0.023, -0.156, 0.892, 0.034, ..., -0.445, 0.231]

384 nombres à virgule flottante (dimensions)

L'idée clé : des textes au sens similaire produisent des vecteurs proches

Visualisation : mots proches = vecteurs proches

Quel modèle pour créer les embeddings ?

On a besoin d'un modèle d'embedding : un programme spécialisé qui sait transformer du texte en vecteurs. Ce n'est pas le même programme que le LLM qui génère les réponses — c'est un outil plus petit et plus rapide, dédié à cette seule tâche.

Notre choix : all-MiniLM-L6-v2

PropriétéValeurPourquoi c'est important
Dimensions384Chaque texte devient une liste de 384 nombres
Taille~80 MBAssez petit pour tourner sur un PC normal
Vitesse~14 000 phrases/secTrès rapide, même sans carte graphique puissante
LangueMultilingueComprend le français (et beaucoup d'autres langues)

Choisi car : gratuit, rapide, tourne en local (pas besoin d'Internet ni de GPU). Parfait pour apprendre et prototyper.

Sentence-Transformers

Sentence-Transformers est une bibliothèque Python (gratuite et open-source) qui fournit des modèles d'embedding prêts à l'emploi. On l'utilise pour charger le modèle et transformer nos textes en vecteurs.


# src/retrieval/embeddings.py
from functools import lru_cache
from sentence_transformers import SentenceTransformer
from src.core.config import get_settings

@lru_cache(maxsize=1)  # Charger le modèle une seule fois !
def _load_model() -> SentenceTransformer:
    settings = get_settings().embeddings
    model = SentenceTransformer(settings.model)  # "all-MiniLM-L6-v2"
    return model

def embed_texts(texts: list[str]) -> list[list[float]]:
    """Générer les embeddings pour une liste de textes."""
    model = _load_model()
    embeddings = model.encode(texts, normalize_embeddings=True)
    return embeddings.tolist()

def embed_query(query: str) -> list[float]:
    """Générer l'embedding pour une question."""
    model = _load_model()
    embedding = model.encode(query, normalize_embeddings=True)
    return embedding.tolist()

Pourquoi normaliser ?

normalize_embeddings=True met tous les vecteurs à la même échelle

Analogie : imaginons qu'on compare des notes d'étudiants. Si un prof note sur 20 et un autre sur 100, les chiffres bruts ne sont pas comparables. La normalisation revient à tout mettre sur la même échelle (par exemple sur 1).

Avantage technique : les calculs de comparaison deviennent beaucoup plus rapides

(Pour les curieux : la distance cosinus se simplifie en un produit scalaire, une opération très rapide pour l'ordinateur)

Similarité cosinus

Comment mesure-t-on si deux textes sont "proches" ? On regarde l'angle entre leurs vecteurs. Plus l'angle est petit, plus les textes parlent de la même chose.

Pourquoi le cosinus et pas la distance "classique" ?

Il existe plusieurs façons de mesurer si deux vecteurs sont proches. Comparons les deux principales :

Distance Euclidienne

Comme mesurer la distance entre deux points sur une carte, en ligne droite

Problème : un texte long et un texte court sur le même sujet peuvent sembler "loin" l'un de l'autre

Similarité Cosinus

Compare la direction des vecteurs, pas leur taille

Avantage : deux textes sur le même sujet sont "proches" quelle que soit leur longueur

C'est pourquoi notre base de données utilise le cosinus : on cherche des textes qui parlent de la même chose, pas des textes de même longueur

Quiz : quels textes sont proches ?

Texte A : "Le Python est un excellent langage de programmation"

Texte B : "Le python royal est un serpent non venimeux"

Texte C : "JavaScript et TypeScript sont des langages web"

PaireSimilarité
A ↔ B~0.35 (mots communs mais sens différent)
A ↔ C~0.72 (même domaine : programmation)
B ↔ C~0.12 (rien à voir)

L'embedding capture le sens, pas juste les mots-clés !

Section 4

Base vectorielle ChromaDB

Stocker et rechercher par similarité

SQL vs Base vectorielle

SQL (classique)


SELECT * FROM docs
WHERE content LIKE '%budget%'

Recherche par mots-clés exacts

"dépenses" ne matche pas "budget"

Base vectorielle


store.search("Quel est le budget ?")

Recherche par similarité de sens

"dépenses" est proche de "budget"

Comment ChromaDB cherche si vite ?

Avec des millions de vecteurs, comparer la question à chacun d'eux serait trop lent. ChromaDB utilise un algorithme malin appelé HNSW (Hierarchical Navigable Small World) pour trouver les vecteurs les plus proches sans tout parcourir.

ChromaDB : initialisation

ChromaDB est une base de données vectorielle open-source et gratuite. Une collection dans ChromaDB, c'est comme une "table" dans une base de données classique : elle regroupe un ensemble de vecteurs.


# src/retrieval/vector_store.py
import chromadb
from pathlib import Path
from src.core.config import get_settings

class VectorStore:
    def __init__(self, collection_name=None):
        settings = get_settings().vector_store
        persist_dir = settings.persist_directory
        Path(persist_dir).mkdir(parents=True, exist_ok=True)

        # Client persistant : les données survivent au redémarrage
        self._client = chromadb.PersistentClient(path=persist_dir)

        # Collection = une "table" dans ChromaDB
        self._collection = self._client.get_or_create_collection(
            name=name,
            metadata={"hnsw:space": "cosine"},  # Similarité cosinus !
        )

Ajouter des chunks


# src/retrieval/vector_store.py — méthode add_chunks()
def add_chunks(self, chunks: list[Chunk]) -> None:
    texts = [c.text for c in chunks]
    ids = [c.chunk_id for c in chunks]
    metadatas = [{**c.metadata, "document_id": c.document_id} for c in chunks]

    # Générer les embeddings pour tous les chunks
    embeddings = embed_texts(texts)

    # Stocker dans ChromaDB
    self._collection.add(
        ids=ids,              # identifiants uniques
        documents=texts,      # texte original (pour le retourner)
        embeddings=embeddings,# vecteurs 384D
        metadatas=metadatas,  # métadonnées (filename, etc.)
    )

Rechercher par similarité


# src/retrieval/vector_store.py — méthode search()
def search(self, query, top_k=5, score_threshold=0.3):
    query_embedding = embed_query(query)

    results = self._collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k,
        include=["documents", "metadatas", "distances"],
    )

    sources = []
    for idx, chunk_id in enumerate(results["ids"][0]):
        # ChromaDB retourne la distance cosinus → convertir en score
        distance = results["distances"][0][idx]
        score = 1.0 - distance  # distance 0 → score 1 (identique)

        if score < score_threshold:  # Filtrer les résultats trop faibles
            continue

        sources.append(SourceDocument(
            chunk_id=chunk_id,
            text=results["documents"][0][idx],
            score=round(score, 4),
        ))
    return sources

Distance → Score de similarité

ChromaDB retourne une distance (plus c'est petit, plus c'est proche). On la convertit en score (plus c'est grand, plus c'est pertinent) pour que ce soit plus intuitif :

score = 1.0 - distance_cosinus

DistanceScoreSignification
0.01.0Textes identiques
0.30.7Très similaires
0.70.3Seuil par défaut
1.00.0Sans rapport

Notre score_threshold = 0.3 filtre les chunks dont le score est trop bas

Combien de résultats garder ?

Deux paramètres contrôlent le nombre de chunks retournés : top_k (maximum de résultats) et score_threshold (score minimum pour être gardé). On les configure dans le fichier de réglages :


# config/settings.yaml
retrieval:
  top_k: 5              # Retourner au maximum 5 résultats
  score_threshold: 0.3   # Ignorer les résultats avec score < 0.3

store.search() appelle embed_query() en interne pour vectoriser la question, puis fait une recherche HNSW dans ChromaDB

Étape 3 : Construction du contexte


# src/retrieval/rag_engine.py
def _build_context_block(sources: list[SourceDocument]) -> str:
    parts = []
    for i, src in enumerate(sources, 1):
        header = f"[Source {i} | score={src.score}]"
        meta_str = ", ".join(
            f"{k}={v}" for k, v in src.metadata.items()
            if k != "chunk_index"
        )
        if meta_str:
            header += f" ({meta_str})"
        parts.append(f"{header}\n{src.text}")
    return "\n\n---\n\n".join(parts)

Résultat : un bloc de texte structuré avec chaque source numérotée et son score

Le System Prompt

Le system prompt, c'est le "briefing" qu'on donne à l'IA avant qu'elle ne voie la question de l'utilisateur. C'est là qu'on lui dit comment elle doit se comporter : être factuelle, citer ses sources, ne pas inventer. L'utilisateur ne voit pas ce texte.


# src/retrieval/rag_engine.py
SYSTEM_PROMPT = """\
You are an enterprise AI assistant.
Answer questions using ONLY the provided context documents.

Rules:
1. Base your answer strictly on the context provided below.
2. If the context does not contain enough information
   to answer, say so clearly.
3. Cite which source documents support your answer
   when possible.
4. Be concise, accurate, and professional.
"""

Clé du RAG : on ordonne au LLM de répondre uniquement à partir du contexte fourni. Cela réduit drastiquement les hallucinations.

L'injection du contexte


# src/retrieval/rag_engine.py
CONTEXT_TEMPLATE = """\
## Retrieved Context

{context}

## User Question

{question}
"""

# Assemblage du message utilisateur
if sources:
    context_block = _build_context_block(sources)
    user_message = CONTEXT_TEMPLATE.format(
        context=context_block,
        question=request.question,
    )

Le LLM reçoit : system prompt (règles) + contexte (documents) + question (utilisateur)

Étape 4 : Génération par Claude

Maintenant qu'on a le contexte (les bons chunks) et la question, on envoie le tout à Claude via son API (un service web fourni par Anthropic). Claude lit le contexte et formule une réponse.

client = anthropic.Anthropic(api_key=api_key)

response = client.messages.create(
    model=settings.llm.model,        # "claude-sonnet-4-20250514"
    max_tokens=settings.llm.max_tokens,  # 4096
    temperature=settings.llm.temperature,# 0.1 (peu créatif)
    system=SYSTEM_PROMPT,
    messages=[{"role": "user", "content": user_message}],
)

answer = response.content[0].text

Section 6

Architecture API

FastAPI et endpoints REST

Pourquoi FastAPI ?

Pour que notre système RAG soit utilisable par d'autres programmes (ou une page web), on a besoin d'un serveur web qui expose des "guichets" (des endpoints). FastAPI est un framework Python qui permet de créer ces guichets très facilement.

  • Rapide : peut gérer plusieurs requêtes en parallèle (on dit "async")
  • Sûr : vérifie automatiquement que les données reçues sont valides
  • Documenté : génère une page de test interactive (Swagger UI)
  • Pythonique : s'appuie sur les types Python qu'on connaît déjà

from fastapi import FastAPI
app = FastAPI(title="Enterprise RAG")

@app.post("/query")
async def query_rag(request: QueryRequest):
    return rag_query(request)

Les routes REST

Chaque "route" est un guichet accessible via Internet. GET = demander des infos, POST = envoyer des données, DELETE = supprimer. C'est le standard du web.

Schémas Pydantic

Pydantic est une bibliothèque Python qui vérifie automatiquement la structure des données. On définit un "schéma" (= un formulaire) : quels champs on attend, de quel type, avec quelle valeur par défaut. Si quelqu'un envoie des données invalides, Pydantic rejette la requête avec un message d'erreur clair.


# src/models/schemas.py (simplifié)
from pydantic import BaseModel

class QueryRequest(BaseModel):
    question: str                     # La question de l'utilisateur
    collection: str | None = None     # Collection cible (optionnel)
    top_k: int = 5                    # Nombre de résultats
    score_threshold: float = 0.3      # Score minimum

class QueryResponse(BaseModel):
    answer: str                       # Réponse générée
    sources: list[SourceDocument]     # Sources utilisées
    query: str                        # Question originale
    model: str                        # Modèle LLM utilisé
    latency_ms: float                 # Temps de réponse

Si on envoie top_k: "abc" au lieu d'un nombre, Pydantic renverra une erreur avant même que notre code s'exécute

async def upload_document(
    file: UploadFile = File(...),     # Fichier multipart
    user: dict | None = Depends(get_current_user),
):
    content_type = file.content_type or "application/octet-stream"
    content = await file.read()       # Lire le contenu binaire
    filename = file.filename or "untitled"

    # Appeler le pipeline complet : parse → chunk → embed → store
    result = ingest_document(content, filename, content_type)

    if result.metadata.status == "failed":
        raise HTTPException(
            status_code=422,
            detail=f"Ingestion failed: {result.metadata.error}",
        )
    return result

La route query


# src/api/routes.py
@router.post("/query", response_model=QueryResponse)
async def query_rag(
    request: QueryRequest,
    user: dict | None = Depends(get_current_user),
):
    QUERY_COUNT.inc()                  # Métrique Prometheus
    start = time.perf_counter()

    result = rag_query(request)        # Appel au RAG engine

    elapsed = time.perf_counter() - start
    QUERY_LATENCY.observe(elapsed)     # Métrique latence

    return result

Monitoring intégré : chaque requête est comptée et son temps de réponse mesuré. Ces statistiques sont exposées au format Prometheus (un outil standard de surveillance) pour pouvoir créer des tableaux de bord et des alertes.

Techniques avancées de RAG

Reranking

Cette section présente des techniques avancées. Elles ne sont pas nécessaires pour un premier projet, mais utiles pour améliorer la qualité des résultats.

Problème : la recherche vectorielle est rapide mais approximative — elle peut remonter des chunks qui ne sont pas les plus pertinents

Solution : un 2e modèle ré-ordonne les résultats avec plus de précision

Recherche hybride

Notre recherche vectorielle comprend le sens, mais elle peut rater des documents contenant un mot-clé exact. La solution : combiner les deux approches.

BM25 (mots-clés)

Comme un Ctrl+F intelligent : cherche les documents qui contiennent les mêmes mots

"budget Q3" → trouve les docs avec ces mots exacts

+

Vectorielle (sens)

Recherche sémantique

"dépenses trimestrielles" → comprend le sens

Hybride = combiner les scores des deux approches pour le meilleur des deux mondes

Fine-tuning des embeddings

Entraîner le modèle d'embedding sur vos propres données pour améliorer la pertinence

Comment ?

  • Collecter des paires (question, chunk pertinent)
  • Fine-tuner le modèle avec ces paires
  • Le modèle apprend votre vocabulaire métier

Exemple : un modèle fine-tuné sur des docs juridiques comprendra mieux "clause résolutoire" qu'un modèle générique

Comment savoir si notre RAG fonctionne bien ?

RAGAS est un outil qui évalue automatiquement la qualité de votre RAG en posant des questions et en analysant les réponses. Il mesure 4 critères :

CritèreQuestion qu'il poseCe qu'il vérifie
Fidélité (Faithfulness)La réponse est-elle fidèle aux documents fournis ?L'IA n'a pas inventé d'information
Pertinence (Answer Relevancy)La réponse répond-elle bien à la question ?L'IA n'a pas répondu à côté
Précision du contexteLes meilleurs chunks sont-ils en premier ?La recherche classe bien les résultats
Rappel du contexteA-t-on trouvé tous les documents utiles ?Aucune info importante n'a été ratée

RAGAS utilise lui-même un LLM pour analyser les réponses — c'est de l'IA qui évalue de l'IA !

Multi-modal RAG et Agents

Notre RAG ne gère que du texte. Mais on peut aller plus loin :

RAG multi-modal

Pas que du texte — on peut aussi chercher dans :

  • Des images (diagrammes, photos...)
  • De l'audio (réunions enregistrées)
  • Des tableaux (données Excel)
  • De la vidéo (présentations filmées)

Agents + RAG

Un "agent" est une IA qui décide elle-même quelles actions faire :

  • Décide quand chercher dans les docs
  • Reformule la question si rien n'est trouvé
  • Combine plusieurs sources
  • Peut naviguer sur le web, envoyer des emails...
